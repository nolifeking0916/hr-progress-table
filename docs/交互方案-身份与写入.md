## 1. 信息架构与导航

### 1.1 核心判断：浏览平面与操作平面分离

现有 3 个视图（事项/明细/甘特）是**同一个数据集的三种密度**，用 tab 切换是对的，不能动。
4 个新功能里只有**进度面板**是另一个"读"，而**创建/更新/身份**是"写"和"系统"，把写操作塞进 tab 栏是错的。

所以定成**两平面**：

```
┌─ 平面 A：浏览平面（tab 切换，4 个视图，同一份筛选状态）────────────────┐
│  事项视图  │  明细视图  │  甘特视图  │  ┃ 进度面板                    │
└──────────────────────────────────────────────────────────────────────┘
┌─ 平面 B：操作平面（常驻按钮，不占 tab 位）──────────────────────────────┐
│  记一笔进展 ●主操作（最高频）   新建任务 ○次操作        身份胶囊 ▾    │
└──────────────────────────────────────────────────────────────────────┘
```

**为什么进度面板进 tab 而不是独立页面**：它和 3 个视图共享同一份筛选（模块/性质/责任人/关键词）、同一套状态徽标（已完成/逾期/进行中）、同一个"事项"实体。做成 tab，面板就是"当前筛选结果的另一种呈现"，心智成本最低，也不需要维护第二套筛选器。

**底部固定条**（`.actionbar--fixed`，仅移动端）：
- 高度 `48px + env(safe-area-inset-bottom)`，`position: fixed; bottom: 0`，`z-index: 40`，背景 `--surface`，上边框 `--border`，加 `backdrop-filter: blur(6px)`。
- 两个按钮并排：**「＋ 记一笔进展」占 62% 宽（实心 `--accent-2`）**，「＋ 新建任务」占 38%（`--surface` + 描边）。比例按实际频次定（更新进度是创建任务的 10 倍以上）。
- 触控目标 ≥ 44px 高。
- 已有页面内容底部要加 `padding-bottom: calc(64px + env(safe-area-inset-bottom))`，否则最后一张卡片被压住。

**移动端 tab 条**：`display:flex; overflow-x:auto; scroll-snap-type:x proximity;` 每个 tab `flex:none; scroll-snap-align:start;`，避免 4 个 tab 在 375px 挤成一团。现有 3 个 tab 是 `.viewtabs__group { display:flex; gap:2px }`，加第 4 个后总宽约 4×62px + 分隔 ≈ 270px，**375px 其实放得下**，但为长文案（如"进度面板⑦"）仍做可滚动保险。

## 2. 功能一：多用户

### 2.1 身份来源：企业微信

**结论：身份 = 企业微信 userid，不自建账号体系。**

- 入口：企业微信工作台「集团人力重点工作进度表」应用 → 打开网页 → 企微 OAuth 免登（`code` 换 `userid`）→ 落 `session` cookie（HttpOnly，SameSite=Lax）。
- 姓名/部门从企微通讯录取，**不在本系统另存一份姓名**（避免人员改名后两边不一致）。
- 需要在企微后台配置「网页授权登录」与**可信域名**（现有部署走自有云服务器 + nginx + 域名，见 `docs/DEPLOY.md` B 方案）。
- 保留一个降级路径：企微不可用时，用服务端管理员签发的**只读链接令牌**（只读用户用，8 小时过期）。

**降级/离线也要能看**：企微会话失效时页面**不阻断浏览**，只降级为只读 + 顶部提示（见 §6.3）。这张表的核心价值是"看"，写只是增值，不能因为登录挂了就不让看。

### 2.2 角色定义

只有 3 个角色（不设第 4 个）：

| 角色 | key | 默认人群 | 说明 |
|---|---|---|---|
| 管理员 | `admin` | 集团行政人事部口径维护人（建议：陈信克 + 1 名备份） | 能改事项级字段、能删、能配角色。**默认名单需业务确认**（见 §9） |
| 填报人 | `editor` | 其余全部企微成员 | 默认角色。能建任务、能给自己负责的事项记进展 |
| 只读 | `viewer` | 外部/借阅人员 | 只能看、只能导出 |

"责任人 / 负责人"**不是角色**，是行级属性，由数据算出 —— 这样才不会和 F5/F6 的现实冲突（陈信克作为负责人覆盖 38 项，但他仍然是 admin 身份，不是"38 个角色"）。

### 2.3 权限矩阵

| 能力 | viewer | editor | admin |
|---|---|---|---|
| 看（受数据范围约束） | ✅ | ✅ | ✅ 全部 |
| 导出 CSV / 打印 | ✅ | ✅ | ✅ |
| 新建任务 | ❌ | ✅（受 §3.6 建模块限制） | ✅ |
| 追加进展 | ❌ | ✅ **仅限"我负责的事项"** | ✅ 全部 |
| 作废自己写的进展 | ❌ | ✅（限自己写的、限 24h 内） | ✅ 任意 |
| 修改事项级字段（起止时间/责任人/负责人/简介） | ❌ | ❌ | ✅ |
| 修改分项、拆分分项 | ❌ | ❌ | ✅ |
| 成员与权限管理 | ❌ | ❌ | ✅ |
| 导出全量明细（含其他模块） | 受数据范围 | 受数据范围 | ✅ |

### 2.4 行级写权限判定（关键规则）

```
canWrite(item, user) =
      role(user) ≠ viewer
  AND ( role(user) = admin
        OR user.name ∈ splitNames(item.责任人)
        OR user.name = item.负责人 )
```

依据 F5/F6 的实际数据，这套判定覆盖度是够的：

| 人 | 事项数 | 说明 |
|---|---|---|
| 汪洋 | 17 | 主力填报人 |
| 盛琳莺 | 16 | 本周 15 条进展，主要更新者 |
| 倪国楷 | 3 | |
| 黄法 / 蒋成 / 李雪 / 汤素琴 / 蔡宇翔 / 朱彦隽 / 陈信克 | 各 1 | |
| 陈信克（负责人） | 38 | |
| 刘玉文（负责人） | 5 | |
| 「各机构人力负责人」 | 1 | **非自然人**，见 §2.6 兜底 |

**边界规则（写清楚，不留模糊）**：
1. **非自然人责任人**：「各机构人力负责人」匹配不到任何企微 userid → 该事项的可写人 = **负责人（陈信克）+ admin**。面板上把该责任人显示为灰体 + 角标「非个人」，并在成员管理页给出「该事项缺少真实责任人，建议改派」的提示。
2. **多人责任人**：责任人列支持换行/顿号分隔（`splitNames()` 现有逻辑），任何一人命中即可写。
3. **代填**：admin 给别人事项代填时，这条进展在源表和详情里都标「代填 · by 陈信克 for 汪洋」，**不隐藏作者**。看板不允许出现"匿名进度"。
4. **editor 能不能给别人建任务**：能，但**只能建在自己是责任人的事项所属的模块下**（防止填报人乱开新模块的事项）。

### 2.5 可见性规则（谁能看）

默认 **全员可见全部 43 项**（源表本来就是集团共享的公开进度表，网页不应比源表更严）。但留一个可配的"数据范围"维度：

| 数据范围 | key | 含义 | 默认 |
|---|---|---|---|
| 全部 | `all` | 43 项全见 | ✅ 所有人 |
| 按模块 | `modules` | 只见指定模块（如某人只看"人力资源规划"） | 无 |
| 仅与我相关 | `self` | 只见自己是责任人/负责人的事项 | 无 |

在**成员与权限页**（`#/admin`）逐人配置。生效方式：
- `all` / `modules`：在服务端过滤，**前端拿到的行数就少了**，不靠 CSS 隐藏（防止越权通过导出拿到全量）。
- `self`：同服务端过滤。
- **面板同步收窄**：可见范围变了，面板的 KPI 分母、模块表、责任人表全部按可见集合重算，并在面板顶部标「当前范围：仅与我相关 · 17 个事项」。

**不做的事**：不给"负责人类型/协调事项"做脱敏、不隐藏任何现有列。理由：源表全员可见，网页若脱敏会让人"网页里没有、表格里有"，反而制造不信任。

### 2.6 姓名 → userid 映射（最脏的一块，必须正视）

源表里只有**姓名字符串**，系统认的是 **userid**。判定"我是不是这个事项的责任人"必须先有映射。

**方案**：
1. 服务端首次同步时，把源表里出现的 11 个责任人名 + 2 个负责人名（共 13 个唯一姓名）去企微通讯录匹配（`wecomcli-contact` / 通讯录 API，按姓名+部门查）。
2. 匹配唯一 → 自动建映射，`confidence=exact`。
3. 匹配 0 个或 ≥2 个 → 进**待人工确认列表**，进成员管理页由 admin 指定。
4. **页面上的姓名永远显示源表原值**（不改写源数据），只是权限判定走映射后的 userid。
5. 每次同步跑一遍对账：企微里离职/改名的人 → 映射标 `stale` → 提示 admin「『黄法』在企微通讯录中不存在，他名下 1 个事项已无人可写，是否改派？」

**必须暴露的风险**：F5 显示 77% 的事项压在汪洋、盛琳莺两人身上。若这两人离职或休假，**没有任何机制会自动把事项转给别人**。成员管理页要对"责任人 7 天以上无任何更新"的事项给出提醒。

| 只读横幅 | 页面顶部（条件渲染） | 「你是只读用户 · 查看与导出可用」 | `.load-error` 复用样式但改成 `--surface-2` 底 |
| 写按钮的禁用 | 全局 | **不写权限的按钮一律不渲染**，不用 disabled（灰按钮会让人反复试） | — |
| 行内「＋」 | 事项卡片 / 事项行 | 只在 `canWrite(item, user)` 为真时出现 | 桌面 hover 显现；触摸设备常显 |

**行内「＋」的位置（具体）**：
- 桌面事项视图：事项名单元格右侧，`rowflags` 徽标之后，一个 18×18 的 ghost 按钮 `＋`，`title="给这个事项记一笔进展"`。
- 移动端卡片：**卡片头部右上角**，与「逾期」徽标同一行，36×36 触控区。
- 展开区（分项组头部）：`.expand__ghead` 右侧，`expand__gcount` 之前，「＋ 记一笔」小文字按钮 —— 这里能精确指定分项。

## 3. 功能二：创建新任务

### 3.1 表单字段表

路由 `#/new-task`，全屏页（非弹层）。桌面左栏表单 + 右栏「实时预览」；移动端单列。

**关于 10、11 两个字段的处理（对应 F8，硬规则）**：
- **负责人类型**：源表 43/43 全是 `B` 且无图例。控件做成下拉、下拉里**只有一个 `B` 选项**——这样它"是一个可以改的字段"（将来口径定了直接加 A），但页面上**不出现任何解释 A/B 含义的文字、不加颜色、不加图例**。下拉里同时提供「（不填）」选项（写空串），因为这是源表允许的。
- **协调事项**：源表整列为空，含义未知。**字段在表单里保留、位置在、label 在**（用户明确要求有这个字段），但控件禁用并显示「暂不填写（口径待定）」。**不提供自由文本输入**——一旦允许填写，就等于在本系统里私自定义了一个源表没有的字段口径，等同于"发明业务含义"。口径定了之后，改成输入框只是服务端一次改动 + 前端放开 disabled。
  - 如果业务方坚持现在就填，退而求其次：做成自由文本，但 label 写「协调事项（口径待定，暂按自由文本记录）」，且在事项详情里对该列的值加 `.badge--warn`「口径待定」角标。**推荐不这么做**。

### 3.2 级联选择器（模块 → 性质 → 事项 → 分项）

**桌面：4 个控件一行，宽度 `200px | 130px | 1fr | 1fr`**，从左到右收窄。

```
┌──────────────┬──────────┬─────────────────────┬──────────────────────┐
│ 一级维度 ▾   │ 二级维度 ▾│ 具体事项 ▾          │ 分项 ▾               │
│ 人力资源规划  │ 人/流程/成本│ 销售提点            │ 茅森提点              │
└──────────────┴──────────┴─────────────────────┴──────────────────────┘
```

**级联规则（精确）**：
1. 未选上一级时，下一级控件 `disabled` 且显示占位文案：「先选一级模块」→「先选二级维度」→「先选具体事项」。
2. 选一级后，二级 chip 只列出该模块**实际存在**的性质（据 F1 交叉表）：
   - 人力资源规划 → 人、流程、成本
   - 招聘与配置 → 人、流程
   - 培训与开发 → 人
   - 绩效管理 → 流程
   - 薪酬福利 → 成本、流程
   - 员工关系 → 人、流程
   - 待定位 → 流程
   这样从物理上杜绝"选了没有数据的组合"。
3. 选一级+二级后，事项下拉只列该组合下的事项（据实测，43 项分布：人力资源规划/流程 5 项最多，人力资源规划/人 7 项…）。
4. 事项选中后，**一级/二级变成只读回显**（因为 F2：事项唯一决定模块/性质）。回显样式：灰底 chip + `title="由具体事项唯一确定"`，避免用户以为可以随便改。

**事项 combobox 细节**：
- 输入框 placeholder「搜事项名或拼音首字母」。
- 下拉最多 8 条 + 底部固定「＋ 新建事项（不在列表里）」。
- 选中已存在的 43 项之一 → 分项下拉自动填入该事项已有分项（单分项事项直接锁为只读 chip，标「该事项只有 1 个分项」；多分项事项给 2–4 个选项）。
- 选「＋ 新建事项」→ 事项输入框变成可编辑文本 + 旁边出现副输入框「分项内容简介」（因为新事项必然是新分项，分项名默认＝事项名）。

**分项新建**：在所选事项下点「＋ 新建分项」→ 事项已定、分项名可输入。注意「其余机构」这类重名是**允许的**（F4），所以分项名**不做全局重名校验**，只做"同一事项内不重名"。

**移动端：4 行堆叠 + 顶部路径条**
```
已选路径：人力资源规划 › 流程 › 销售提点 › 茅森提点
（未选部分用 --text-3 灰字占位「—」）

一级维度  [chips 横向可滚动]
二级维度  [chips 横向可滚动]
具体事项  [combobox 44px 高]

```
路径条在移动端很重要：4 级选择在窄屏上很容易"选着选着忘了选到哪"，一条路径一眼可见。

### 3.3 表单页的其它交互

**右侧预览（桌面 ≥1024px，360px 宽）**：实时渲染这个新事项在事项视图里长什么样——模块色点 + 事项名 + 责任人 chip + 开始·完成 + 一条空的「最新进展」位（显示「尚无进展记录」）。
作用：让填表的人看到结果，而不是提交完才发现填错。移动端无预览。

**草稿**：
- 每次字段变更 debounce 400ms → 写 `localStorage['hr.newtask.draft.v2']`。
- 再次进入 `#/new-task` 且存在草稿 → 顶部 amber 条：「上次未保存的草稿（保存于 10 分钟前） · 继续填写 · 放弃」。
- 提交成功或主动点「放弃」→ 清空草稿。

**离开提醒**：表单有改动时 `beforeunload` 拦截（桌面）；移动端不做（切走就丢，但草稿已存）。

**提交按钮**：
- 桌面右下固定条：「取消」ghost + 「创建任务」实心。
- 移动端底部固定条（同 §1.3 样式，占满宽度）。
- 提交中：按钮变 `保存中…` 且禁用，**不关闭页面**。

**提交后的三态**：
| 情形 | 表现 |
|---|---|
| 成功 | toast 4s：「已创建：销售提点 · 茅森提点 · 同步到源表约 1 分钟」+ 内嵌按钮「现在记第一条进展」（点了就带着这个事项的上下文打开记一笔弹层）+「查看」 |
| 校验失败 | 首个错误字段下方红字 + 滚动到该字段 + 聚焦；顶部汇总「有 2 处需要修改」 |
| 服务端失败 | 字段区下方 amber 块：「保存失败：网络异常。草稿已保留，可重试。」+「重试」按钮 |

**写回源表（F9 的落点）**：
- 创建 N 个分项 → 向「重点工作进度 v2」**追加 N 行**，每行 15 列，`进展日期` = 开始时间，`进展内容`/`当日计划` 留空。
- 这 N 行会被现有 `build_rows.py` 的清洗规则判为「待补」（进展与周计划都为空），页面上带 `.badge--warn`「待补」。
- **必须同步改 `docs/口径说明.md` §3**：把「待补」的定义补一句——「新建事项在首次记进展前也显示『待补』，表示该分项尚未填报进展，不是数据错误」。否则 admin 会以为新建流程在造脏数据。这是"新建任务"功能**必须连带的一次文档改动**，不是可选项。

### 3.4 事项序号：新任务不给号

源表序号已经撞号（13 和 20 各对应两个事项，21 个序号承载 43 条事项，见 `docs/口径说明.md` §数据问题 1）。若网页再自动分配序号，撞号会更严重。

**决定：新任务不写源表的「事项序号」列（留空），网页展示为「新」徽标，排序时沉底。**
依据：`docs/口径说明.md` 已明确「源表今天新增的两行没填序号，抽取时按顺序补了位」——**空序号是源表已有的既有行为**，不是新发明。抽取器 `build_rows.py` 会自动补位，网页照常能显示。

**副作用要认**：抽取器"按顺序补位"意味着新任务插在源表末尾时，它会拿到一个序号，而这个序号可能与人工填的号冲突。建议抽取器对"空序号"行统一给 `seq = null`，网页显示「新」并排在末尾——这是**对现有脚本的一处改动**，列为实施项。

### 4.3 最小输入路径（速度是硬指标）

依据 F3：**39/43 的事项只有 1 个分项**。所以最常见路径必须是 **2 次输入**：

```
选事项（1 次点击，或从 E2/E3/E4/E5 直接带入，0 次）
  → 日期已默认今天（0 次）
  → 分项自动带出并只读（0 次）
  → 写内容（1 次）
  → 点「保存」（1 次）
────────────────────────────
共 2 次交互
```

**「分项」控件的处理**：
- 单分项事项（39 个）：显示为只读 chip，**不给下拉、不给焦点、不参与校验**。
- 多分项事项（4 个：销售提点 / 研创院工程考核方案 / 职位职级调整 / 后台月薪标准调整）：显示为 `select`，默认选**第一个未在今天记录过分项**的分项（省一次点击），下拉里标注每个分项今天是否已有进展（✓ 已有）。

**「同时记一条当天计划」默认不勾**。理由：最常见动作不需要计划；勾选框是 0 成本的"可选项"，但让它默认展开会变成 1 次额外输入。勾选后第二个 textarea 展开，且**两个字段可以只填一个**（源表两列各自独立，允许进展空/计划空）。

**日期控件**：
- 默认今天，`max = 今天`（进展不能是未来日期——未来日期在口径里属于"计划"）。
- `min = 今天 - 90 天`（补录窗口）。更早的补录需要走 admin（防止有人补半年前的内容污染"最新进展"）。
- 允许选过去日期 → 这会插入到历史位置，页面上该事项的"最新进展"不变（因为口径是按日期取最新），但**展开区的逐日表里会多出一行**。

### 4.4 移动端单手规格（375px 硬指标）

这是本功能最难的部分，逐条给死：

| 项 | 规格 |
|---|---|
| 容器 | `position: fixed; inset: 0; height: 100dvh`（用 `dvh` 而非 `vh`，避免地址栏收起导致底部按钮被推上去） |
| 顶部 | 拖拽条 20×36px 居中（`--border-2`），标题行 44px，含「记一笔进展」+ 「×」（44×44 触控区） |
| 上下文条 | 高度 44px，**只显示事项名 + 模块色点 + ⌄**；点 ⌄ 展开看「责任人 / 负责人 / 起止时间 / 当前状态」 |
| 标签布局 | label 在左（`--fs-xs`，`--text-3`，宽 4em），控件在右。**所有输入行的控件右边缘对齐**，拇指落点固定 |
| 输入框字号 | **`font-size: 16px`**（<16px 时 iOS Safari 会自动放大页面，滚动位置会跳） |
| textarea | `min-height: 132px`（约 5 行），`line-height: 1.6`，`padding: 10px 12px` |
| 底部条 | 固定底部，`padding-bottom: env(safe-area-inset-bottom)`；两个按钮高 44px，「保存」实心占 40%、「保存并继续下一条」ghost 占 45%、「取消」文字按钮 |
| 键盘适配 | 监听 `window.visualViewport` 的 `resize`/`scroll`，把键盘高度写进 CSS 变量 `--kb`，底部条 `transform: translateY(calc(-1 * var(--kb)))`。**不做这个，手机上底部「保存」会被键盘顶掉——这是移动端表单最常见的致命伤** |
| 单手可达 | 上半屏只放只读信息（上下文条、最近进展），所有可点元素在屏幕下半 55% |
| 无障碍 | 打开时焦点进 textarea；`aria-modal="true"`；`Esc` 关闭；焦点圈定在弹层内 |

### 4.5 「保存并继续下一条」（批量补录的杀手锏）

场景：销售提点有 3 个分项（茅森/恐龙/聚力），我 3 个分项各写了一行；或者我今天要补 5 个事项。

保存后**不关弹层**，顶部出现一条绿色状态条：
```
╭────────────────────────────────────────────────────────────╮
│ ✓ 已保存 10-24 候选人分析前置              [结束]           │
╰────────────────────────────────────────────────────────────╯
```
同时：
- 事项上下文**切到下一条**：优先同事项的下一个分项（4 个多分项事项）；单分项事项则切到「我负责的下一个今天还没更新的事项」（按"末次进展距今最久"排序）。
- 日期**保持不变**（批量补录同一天）。
- 内容框清空并重新聚焦。
- 「结束」按钮退出。

这让"补 5 条进展"从 5 次开弹层 + 5 次选事项变成 1 次开弹层 + 5 次打字。

### 4.6 最近进展参考条（防止重复写）

弹层底部一条**默认折叠**的摘要条：「最近进展（该事项） · 10-22 已完成初稿已提报 · 10-19 已通知相关方」。

- 展开显示该事项最近 3 条非空进展（日期 + 内容前 60 字）。
- 作用：① 避免把昨天写过的话再写一遍；② 提供上下文，让新进展写得连贯。
- 成本：一次折叠交互，不干扰主路径。

### 4.7 写入后到源表的同步语义

写入是 **append 一行**（F9），源表是多人共同维护的，所以要明确三件事：

1. **网页的即时反馈 ≠ 源表已更新**。提交成功后立刻在页面插入该行（乐观更新），行尾标「同步中」。
2. **同步状态三态**，在行尾用小徽标表达（复用 `.badge`）：
   - `同步中`（`--surface-3` 灰）
   - `已同步`（不显示徽标，成功即隐去）
   - `同步失败`（`--amber`）→「重试」按钮
   - `源表冲突`（`--amber`）→「查看差异」
3. **服务端串行化**：同一张源表（同一 docid）的写入由服务端排队执行，读-改-写带版本号，避免两人同时追加到相邻行造成错位。

### 4.8 离线与队列

- 提交时若无网络：**先写本地队列** `localStorage['hr.outbox.v1']`，页面立刻显示「已保存（待同步）」，页面顶部出现全局条：「离线 · 2 条待同步」。
- 联网后自动重放（指数退避，最多 5 次）。
- 重放成功 → 队列清空，行尾徽标消失。
- 重放失败（403/409）→ 队列项标红并**保留**，在队列面板里给「重试」和「查看原因」。
- 队列在页面关闭后仍在（localStorage），下次打开自动重放。

### 4.9 撤销 → 改叫「作废」

企微在线表格的 `rows` 能力只有 **append**，没有删除行。所以真撤销做不到。

**决定：按钮叫「作废」而不是「撤销」**，语义更准确：
- 提交后 toast 停留 5s：「已保存 ✓　[作废]」。
- 点「作废」→ 服务端把该行标记 `voided`（软删除），并**向源表追加一行标记**（进展内容写「（作废：2026-10-24 由汪洋作废）」）。
- 审计链完整：源表里能看到"有一条进展被作废了"，而不是凭空少一行。
- 页面上被作废的行：内容删除线 + 灰字 + `.badge--muted`「已作废」。
- 谁能作废：作者本人（24h 内）或 admin。

## 6. 空 / 加载 / 错误 / 冲突态

### 6.1 加载态

引入服务端后首屏变成异步。分层处理：

| 层 | 加载表现 |
|---|---|
| 页头/筛选区/tab 条 | **立即渲染**（本地就有），不等网络 |
| 表格体 | 3 行灰色骨架条（`.skeleton`，高度 30px，背景 `--surface-3` 呼吸动画，`prefers-reduced-motion` 时改为静态） |
| 面板 KPI | 4 张卡的数字位显示 `—`，骨架占位 |
| 身份胶囊 | 显示灰色骨架圆点 + 「识别中」；**身份没拿到之前不渲染任何写按钮** |
| 数据刷新（后台轮询） | **不整页重载**，只更新变化了的行；表格整体加 `opacity:.6` 过渡 120ms 表示"正在同步" |

**离线兜底**：服务端不可达 → 直接回落读 `data/rows.js`（现有静态包），页面顶部 amber 条：
> 当前为**离线快照**（数据截至 2026-10-24）。写入功能暂不可用。

**这是刻意保留的降级路径**：现在的页面双击 `index.html` 就能用，加了服务端之后这个能力不能丢——现场演示、断网、内网穿透不通时，页面必须还能看。

### 6.2 空态（区分 5 种，不能都用一句"暂无数据"）

| 场景 | 文案 | 附加 |
|---|---|---|
| 筛选后无事项 | 「当前筛选条件下没有事项。请调整筛选或点『重置』。」 | （现有文案，保持不变） |
| 明细视图无行 | 「当前筛选条件下没有明细行。」 | 现有文案 |
| 面板·逾期为空 | 「🎉 当前范围内没有逾期项。」 | 庆祝语气 |
| 面板·本周动态为空 | 「本周还没有人记进展。」+ 按钮「记一笔」 | 引导 |
| 面板·我负责的事项为空 | 「你目前没有被指派的事项。」+「去事项视图看看全部」 | 引导 |

### 6.3 错误态分级

| 错误 | 出现位置 | 文案 | 动作 |
|---|---|---|---|
| 未登录 / 企微会话失效 | 页面顶部条（非阻断） | 「登录已过期，正在重新获取身份…」；重试失败则「无法获取企微身份，当前以只读方式浏览。」 | 「重新登录」按钮 → 走企微 OAuth |
| 无写权限（403） | 表单内联 | 「你没有权限给『XX』记进展 —— 你不是该事项的责任人或负责人。」 | 「找负责人代填」按钮（复制一条带上下文的企微消息） |
| 离线 | 顶部条 | 「离线 · N 条待同步」 | 展开队列 |
| 写入失败（5xx/超时） | 行尾徽标 + toast | 「保存失败：网络异常。草稿已保留。」 | 「重试」 |

| 服务端 500 | toast | 「服务异常」 | 「复制错误信息」（便于群里报障） |
| 表格行加载失败 | 该区块 | 「这一块没加载出来。」 | 「重新加载」（只重载该区块，不整页刷新） |

## 7. 关键 UX 风险

按「会不会真的伤到用户」排序。

### R1（最高）· 源表是多人共编的，网页写入会和人直接改表冲突
- **风险**：陈信克在表格里改了进展，网页这边同时写入 → 谁覆盖谁。源表 v2 是长表，行是独立的，一行被改不影响别的行，所以**冲突面比"原表"小很多**（原表 F 列是一格多行文本，两人写同一格必冲突）。
- **对策**：① 写入一律 **append**，不改已有行；② 只有 admin 的"改事项级字段"才 update 单元格，且 update 前读原值比对，不一致则报冲突；③ 冲突文案必须说清"你的内容没有写入"。
- **残余风险**：源表里已有的行被人在表格里删了/改了，而网页缓存的旧值还在 → 面板数字会短暂不一致。加一条 60s 轮询 + 「数据已更新」提示条。

### R2 · 「最新进展」的读取口径与追加写入天然冲突
口径说明写死：「按事项序号↑ / 进展日期↓ 排序后，每个事项块第一条非空进展就是最新进展」。**如果补录一条 10-15 的进展（在 10-20 之后写）**，最新进展仍然是 10-20 那条——补录不会改变"最新进展"，但会改变"末次更新"（谁什么时候写的）。这两个时间在面板上会不一致。
- **对策**：面板上明确区分两个时间——「末次进展日期」（业务时间，10-20）和「末次更新」（录入时间，今天）。KPI 卡「本周更新 20 条」统计的是**录入周**，不是进展日期周。口径写在 ⓘ 里。

### R3 · 77% 的事项压在两个人身上，且没有自动改派
- **风险**：汪洋或盛琳莺休假/离职，33 个事项静默无人可写，且没人会立刻发现（页面照常显示，只是没人能记进展）。
- **对策**：① 面板「责任集中度」提示；② 成员管理页对"责任人 7 天无更新"的事项标红；③ server 侧每日检查"存在无人可写的事项"（责任人姓名在通讯录里查无此人）→ 站内通知 admin。

### R4 · 姓名 → userid 映射是整个权限体系最脆弱的一环
- **风险**：源表只有姓名。两个人重名（源表里有 11 个姓名，其中"陈信克"既是负责人也是责任人）、一个人改名、一个人离职，都会造成权限误判——**误判成"可写"比误判成"不可写"危险得多**。
- **对策**：① 映射表带 `confidence` 与人工确认状态；② **未确认的映射默认按"不可写"处理**（宁可拦住，不可放开）；③ 通讯录查无此人的责任人 → 该事项只有 admin 可写；④ 每次同步做对账，把失效映射报给 admin。

### R5 · 新建事项与现有 43 项重名会破坏前端模型
- **风险**：`app.js` 用 `item.name` 作 `groups` 的 key、`srcByName[item.item]` 作索引。新建一个叫"销售提点"的事项会让 43 项变 44 项但其中两条同名 → 分组塌陷、最新的进展串行、序号再撞一次。
- **对策**：服务端**强校验事项名全局唯一**（与 43 项已有名字冲突时拒绝并给出已有事项的跳转链接）；`build_rows.py` 的 `srcByName` 改成"同名取全部、按来源 id 消歧"。

### R6 · 写进去就是集团台账，没有回收站
- **风险**：一句写错的话进了源表，影响所有看表的人。
- **对策**：① 提交后 5s 内可「作废」（§4.9）；② 作废是 append 一条标记行，审计链完整；③ 表单支持草稿，误触不会立刻发。

### R7 · 移动端输入框 <16px 导致 iOS 自动缩放，滚动位置跳变
- **风险**：这是移动端表单第一常见的"页面跳了、内容填没了"。
- **对策**：所有输入控件 `font-size: 16px`（移动端断点内），并且**日期输入、select 也一样**。

### R8 · 手机软键盘顶掉底部「保存」按钮
- **风险**：用户写完内容找不到保存键，放弃。
- **对策**：`visualViewport` 监听 + `--kb` CSS 变量（§4.4）；底部条永远可见。

### R9 · 视觉密度分裂：浏览 13px vs 写入 14–16px
- **风险**：表单沿用 13px 会很难填（尤其手机上）；沿用 16px 又和现有表格"不像一个产品"。
- **对策**：明确分两层——**浏览层沿用现有 13px 高密度**（表格、面板），**写入层放大到 14px（桌面）/ 16px（移动）**。这是钉钉/飞书的通行做法，不算不统一。表单所在的 `#/new-task` 页面有自己的 `body` 类，作用域限定。

### R10 · 深色模式下新增图表/浮层配色不跟随
- **风险**：`--accent` 在深色下变成浅蓝 `#9cc0e8`；新增的 KPI 卡、堆叠条、徽标如果写死颜色，深色下会瞎。
- **对策**：新增样式**一律用 CSS 变量**，不写死色值；新增一张堆叠条的颜色用 `--accent-3` / `--amber` / `--border-2` 三个已有变量，不新增语义色。验收时必须**深浅两色都过一遍**（现有代码已有 `@media (prefers-color-scheme: dark)` 全套变量）。

### R11 · 明细视图已经很宽（2080px），加列会更难用
- **风险**：为了显示"作者""同步状态"再加 2 列 → 2160px。
- **对策**：明细视图**不加列**。作者信息只加在**事项视图展开区**（逐日记录行里，进展内容后加一个小灰字「· 汪洋 10-24」）。同步状态徽标也只在这 3 个视图出现。

### R12 · 源表 v2 与智能表格甘特镜像是两个文档
- **风险**：写入在线表格**不会**自动更新智能表格镜像 → 甘特镜像会静默滞后。
- **对策**：实施前必须先验证镜像同步机制（脚本 or 自动）；若是脚本，纳入同一条 cron；若是手动，在镜像文档里贴一行「数据更新于 X」。**这是一个上线前必须回答的问题，不能留到上线后。**

### R13 · 权限判定靠姓名匹配，而责任人字段格式脏
- **风险**：`splitNames()` 能处理换行/顿号/斜杠，但源表里有一条责任人是「各机构人力负责人\n汪洋」——多值 + 其中一个不是人。
- **对策**：权限判定统一走**服务端**（前端不算权限，只做 UI 隐藏；服务端是唯一裁决者）。非自然人责任人走兜底规则（§2.4）。

### R14 · 首次上线的"写"与现有"只读"页并存，用户不知道哪个是真的
- **风险**：网页里改了，源表里没同步；或者源表里改了，网页没刷新。
- **对策**：① 页头「数据截至」扩成「数据截至 2026-10-24 · 3 分钟前同步」；② 写后立刻显示「同步中」徽标，源表更新后徽标消失；③ 60s 轮询 + 顶部「数据已更新」提示条；④ 口径说明里加一节「网页与源表的关系」。
